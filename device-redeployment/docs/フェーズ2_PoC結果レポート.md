## 3. 工場出荷リセット（初期化）の扱いについて（技術仕様に基づく合意事項）

要求事項定義書 4.1「対象とする作業範囲」およびPoC設計書 6.1「検証手順」は、工場出荷リセット（完全初期化）を含めた一連の流れを自動化の対象として想定していました。

実機検証の結果、**工場出荷リセット後のセットアップウィザードをADB経由で遠隔から自動突破することは、構造的に不可能である**ことが判明しました。

- 工場出荷リセットを実行すると、ADBの認可（USBデバッグの許可情報）そのものが端末側で失効します。
- 認可が失効した状態ではADBによる `uiautomator dump` を含むあらゆる操作ができません。
- 認可を再度有効にするには、端末の画面を人が直接タップしてセットアップウィザードを完了し、USBデバッグを再許可する必要があります。
- つまり「ADBが使える状態」と「セットアップウィザードが表示されている状態」は両立し得ません。

この結論に至るまでに、`device_provisioned`／`user_setup_complete` フラグの直接書き換え、Google標準のセットアップウィザードactivityの強制起動、SHARP独自のセットアップウィザードactivityの強制起動など、遠隔から突破する方法を複数試行しましたが、いずれも失敗（システムの不安定化を含む）に終わっています。

以上の技術的制約を踏まえ、**工場出荷リセットおよびセットアップウィザードの完了は貴社側で手動対応いただく**方針を貴社と合意しました。本自動化（`main_phase2.py`）は、手動でのリセット・ウィザード完了後、USBデバッグが有効な状態から先の工程（Wi-Fi設定・APN設定）を担います。

なお、この手動対応は貴社の現行の手作業運用の一部（要求事項定義書 1.1「背景・目的」記載のとおり、現在すべて手作業で実施されている工程）と同じ操作であり、新たに追加の作業負担が生じるものではありません。この合意に伴い、`--skip-wizard` オプション（ウィザード関連チェックを省略し、Wi-Fi／APN設定から開始する）が本番運用における標準の起動方法となっています。

## 4. 検証項目別の結果（PoC設計書 5章 項目1・2・5・7）

### 4.1 機種横断でのフロー成否（項目1）

4機種すべてで、Wi-Fi接続確認〜APN設定〜保存までのフローが、人手を介さず完走することを実機で確認しました。

| 機種 | 直接確認済み成功日 | 実機検証で見つかり、修正した機種固有の課題 |
|---|---|---|
| SHG10 | 2026-09-11／2026-09-17（後述の回帰修正後）／2026-09-22 | かな／英数キーボードモードの切替座標の個体差、およびモード状態が時間とともにドリフトする問題 |
| SHG07 | 2026-09-15／2026-09-22 | 同上（かな／英数キーボードモード切替） |
| SOG07 | 2026-09-17（初回完走）／2026-09-22（後述のSIM起因課題の解決確認） | 数字専用キーパッドの切替座標・入力方式がテキスト項目と異なる点、実SIMのMNC値と共有設定値の不一致 |
| SOG08 | 2026-09-17／2026-09-22 | 初回から大きな修正なく完走（他3機種で必要だった個別対応が不要だった） |

いずれの機種も、最終的には `python src\main_phase2.py --skip-wizard`（後述のとおり2026-09-22以降はシリアル指定不要）1コマンドで、Wi-Fi接続・APN登録・保存確認までを無人で完走します。

**留意点：** 上表は各機種で少なくとも1回以上、無人での完走を直接確認したという事実を示すものであり、PoC設計書7章の成功判定基準にある「各機種で95％以上のフローが完了すること」を正式に検証する、同一条件での複数回試行による成功率の統計的な計測ではありません。8章に記載のとおり、正式な成功率計測は今後の課題です。

### 4.2 1台あたりの処理時間（項目2）

2026-09-22実施の4台同時並列実行（実ログより）で、Wi-Fi（接続済みのため実質スキップ）〜APN設定完了までの所要時間は以下のとおりでした。

| 機種 | シリアル | 所要時間（起動指示〜LOGIN_INSTALL到達） |
|---|---|---|
| SHG10 | 352063910272451 | 約84秒 |
| SHG07 | 353681650397052 | 約88秒 |
| SOG07 | HQ632M1012 | 約83秒 |
| SOG08 | HQ63460161 | 約94秒 |
| **平均** | | **約87秒／台** |

**留意点（重要）：**
- これは**1回の実機並列実行から得られた参考値（n=1）**であり、正式な複数回計測ではありません。実行ごとのばらつきは未計測です。
- Wi-Fiは検証時点で接続済みだったため、Wi-Fi新規接続にかかる時間は含まれていません。
- 3章の合意により工場出荷リセット・ウィザード完了は貴社側の手動対応となったため、この所要時間には**含まれていません**。本番でのフェーズ2全体のスループットを見積もる際は、貴社側の手動リセット・ウィザード完了に要する時間を別途考慮いただく必要があります。
- 要求事項定義書9章「非機能要件」では、1台あたりの平均所要時間を暫定的に5分と仮定し、200台／時間の目標達成には常時20〜30スロット程度の並行稼働が必要と試算していました。今回実測したAPN設定部分（約87秒／台）は、この暫定仮定（5分）を大きく下回る結果です。ただし4台での実行結果であり、20〜30台規模での同時実行時にも同水準を維持できるかは未検証です。スロット数の最終設計は、複数回・より多台数での計測を経て確定することを推奨します。

### 4.3 USB給電安定性（項目5）

**未実施。** PoC設計書の判定基準は「20台同時接続を2時間以上維持し、意図しない切断が発生しないこと」ですが、今回の実機検証では最大4台までの同時接続にとどまり、長時間の同時接続維持試験も実施していません。8章に記載のとおり、今後の課題として残っています。

### 4.4 失敗検知・再試行の動作（項目7・フェーズ2部分）

オーケストレーション層（要求事項定義書 7章の状態遷移・疑似コードに対応する実装）において、以下の再試行・エスカレーション機構を実装し、自動テスト（261件、すべて合格）で検証済みです。

- 1台の処理失敗を検知した場合、そのスロットのみ `INIT_APN` からやり直す（他スロットの処理には影響しない）
- 再試行回数が上限（既定3回、`--max-retries` で変更可）を超えた場合、`ESCALATED` 状態として記録し、処理を停止する
- 1台の失敗・不明なモデル等が、並列実行中の他の端末の処理を止めない設計になっている（`_run_one_device()` は例外を投げず、必ず結果を返す）

また、実機検証を進める過程で、APN保存直後の一覧反映タイミングのずれなど、実際に発生した一時的な不整合をソフトチェック（即時確認＋一定時間後の再確認）が正しく吸収する挙動も、副次的に複数回確認しています。

**留意点：** PoC設計書 6.1 手順5にある「意図的に端末を切断する等して失敗を発生させ、失敗検知・再試行の動作を確認する」という、意図的な障害注入による実機での動作確認は、独立した検証項目としては未実施です。再試行・エスカレーションの仕組み自体は実装・自動テストとも完了しているため、実施自体は低コストで行えると見込んでいます。8章に記載のとおり、今後の課題です。

## 6. 実機検証を通じて判明した主な技術的知見

机上の検討だけでは判断できなかった、実機特有の挙動を複数確認しました。PoC本来の目的（実測に基づく本番設計判断材料の取得）に沿った成果として整理します。

1. **キーボードのかな／英数モードが `uiautomator dump` から不可視の内部状態であること。** 直接読み取る手段がないため、1文字だけ入力して読み戻し確認する自己補正方式を実装。切替座標は機種ごとに実機で確認する必要があり、かつ同一機種でも時間経過とともにモードがドリフトする（1度確認済みでも恒久的に安全とは言えない）ことも判明しました。
2. **APN設定への標準インテント（`android.settings.APN_SETTINGS`）が、実際のSIM回線と連動しない制限された画面に到達してしまうこと。** 実機ダンプにより、Wi-Fi設定画面経由でSIM個別のモバイルネットワーク設定に入る正しい経路を特定し、修正しました。
3. **上記の正しい経路上で、目的の項目がシステムナビゲーションバーの境界に重なり、タップが正しく届かないことがあること。** スクロール操作を追加して解消しました。
4. **実SIMのMCC/MNC値と設定ファイル上の値が一致しない場合、Android側がAPN保存を無言で拒否すること（エラー表示なし）。** SOG07の実機で発見。個体ごとに通信設定を上書きできる仕組み（`device_overrides`）を追加しました。
5. **新規APN追加時、Android自身がSIMからMCC/MNCを自動入力する仕様があること。** 上記4の根本原因はこの自動入力済みの正しい値を自動化側が誤って上書きしていたことであり、既存値がある場合は上書きしない判定ロジックへ改善しました。
6. **セットアップウィザードの完全自動化が構造的に不可能であること。** 3章のとおり、工場出荷リセット後のADB認可失効という技術的制約により判明し、貴社との運用分担の合意に至りました。

## 7. 追加実装：デバイス自動検出機能

当初計画にはない改善として、接続された端末のシリアル番号・機種をコマンド側で手動指定する必要をなくす機能を追加しました。

`python src\main_phase2.py --skip-wizard` を実行するだけで、接続中かつ認可済みの全端末を `adb devices` と `getprop ro.product.model` により自動検出し、機種を特定したうえで並列実行します。機種が特定できない端末は、無視して進めるのではなく明確にログへ出力し除外する設計としており、不確実な一致による誤動作を防いでいます。

2026-09-22、4台同時接続の実機でこの自動検出が正しく機能することを確認済みです（4台とも正しい機種として検出のうえ、全台成功）。今後、貴社側で異なる実機を接続する際も、コマンドやコードの変更なしに運用いただけます。

## 9. 次フェーズへの移行判断（提案）

PoC設計書10章に基づき、フェーズ2の結果をもとにフェーズ2本番スクリプト開発への移行可否と、フェーズ3の詳細スケジュール確定が求められています。

本レポートの内容を踏まえた提案は以下のとおりです。

- **フロー成否（項目1）・失敗検知の仕組み（項目7）は、実装・実機確認とも完了しており、フェーズ2の本番スクリプトとして運用を開始できる状態にあると考えます。**
